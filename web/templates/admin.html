Panel PIN

…
Set a PIN 4 digits — the panel asks for it once per browser, per day

Gates the settings on this page and everything that moves him — servos, rest/relax, calibration, the cart's drive controls and who may drive it. Deliberately left open: the live status, the camera, the sound board, and making him speak. The cart's STOP is never gated — you should not be typing a PIN while a 350 lb base rolls at a wall. The robot's own machines on the wired LAN (10.0.0.x) are exempt, because the Pis call these endpoints constantly and cannot type. The chest touchscreen asks for the same PIN, and keeps working with this machine switched off.

Know what four digits is worth. The panel speaks plain HTTP, so the PIN crosses the network in the clear, and ten thousand combinations is not many — wrong guesses are rate-limited to make that slow, but this is a barrier against a curious stranger on the access point, not a secret. The AP password and physical access are still the real perimeter. Changing or removing the PIN signs out every browser, including this one.

MyRobotLab handoff

Release hardware to MyRobotLab hand off servos, audio & camera

When ON, this app drops the I2C servo bus (PCA9685), the USB audio card, and the Pi camera so MyRobotLab (port 8888) can drive them instead — only one stack may own the hardware at a time. FRED's own servo, voice, and camera controls are disabled until you turn this back off. This is a live switch (applies immediately, no Save needed) and the choice persists across reboots.

Event mode

He is in front of the public shorter answers, slower driving
…

A hall full of children is not a workshop. On, FRED keeps spoken answers under 25 words — the mic is deaf while he talks, so a long answer cannot be interrupted by voice — and the cart's speed ceiling drops to 120 of 300 on a machine that weighs 350 lb. It is not a safety interlock; the e-stop and the deadman are. It is how you avoid needing them. Live (no Save needed); persists across reboots.

Audit mode

Dry run — no sound, no motion interact normally; nothing physical happens

When ON, FRED stays fully interactive — the chat box, the wake word, the servo sliders and face tracking all work, and the transcript and on-screen face behave exactly as normal, lip-sync included. But no audio reaches the speaker, no pulse reaches a servo, and the cart will not drive. The servo readouts keep tracking the commanded angles, so you can watch what he would have done. Unlike the handoff above, nothing is disabled and the hardware is not given away — the servos simply hold their pose rather than being relaxed, so nothing sags. Switching back off returns the servos to rest, since the readouts and the hardware will have drifted apart during the audit. Live switch (no Save needed); persists across reboots.

Needs the Vosk model + a microphone. Open-ended questions also need an Anthropic API key in config/secrets.env — built-in commands work without one. Raise the lead-in (≈0.4–0.6 s) if the speaker clips the first word or two while it wakes up; leave it at 0 for a device that starts instantly.

Lip-sync trim nudges the jaw against the voice. The lead-in is already compensated exactly, so this only corrects what's left — ALSA buffering and the servo's own travel time. Positive if the mouth moves before you hear him, negative if it lags. ±0.2 s is usually plenty; applied live, so tweak it while he's talking.

The mic's analog gain is already maxed, so Mic sensitivity boosts the signal in software. 1× is off; try ≈2× for quiet or distant speech. Past ≈3× it mostly amplifies room noise and clips loud words, which hurts recognition — applied live, no reboot needed.

Misses are what the command matcher did not recognise — the set to read after an event. A misheard word shows up here as an A.I. round trip that should have been a reflex: he heard “servers”, the matcher knows “servos”. Fix the vocabulary or the pattern, not the child. Bystander conversation is never logged — only what passed the wake word or was typed at the panel.

Developer

Claude terminalbrowser shell on any of the three

Opens a full terminal (ttyd + tmux) in a new tab — run claude, git, tests, etc. to work on FRED without SSH. Type claude to start; your session persists in tmux if you close the tab, and it is the same session however you got in.

All three are served by the NUC: the Pi terminals ssh out from here rather than each Pi running its own. The robot LAN (10.0.0.0/24) is not routable from the house network, so a ttyd on a Pi would be unreachable from a laptop — this way every terminal works wherever this panel does. Never forward these ports to the internet.
